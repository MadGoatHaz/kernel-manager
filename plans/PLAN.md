## DECISIONS

### D1 (Feature A) — entry point = a non-interactive tree row with a right-click action; NOT checkbox-Execute, NOT a bottom-bar button
- **Chosen:** one row appended at the end of `init_kernels_tree_widget` (after the kernel loop — both rebuild paths, ctor :391 and `init_kernels()` :729, inherit it): PkgName = **`tr("Install from directory…")`**, Version = `—`, Category = `Local`, Installed = `—`, Check cell = a **non-interactive `QLabel`** folder glyph (theme `folder-open` → `folder` → centered `📁` text fallback — the D3 lock-label recipe verbatim), flags = `ItemIsEnabled | ItemIsSelectable` only (**no** `ItemIsUserCheckable` ⇒ no checkbox, no `itemChanged`/`build_change_list` signal paths, invisible to the worker). Tooltip (QStringLiteral, deferred-lupdate per the D3/E14 precedent): "Install a locally built kernel package from a folder: right-click to choose the folder containing the built *.pkg.tar.zst package(s)." Right-click on the row ⇒ `on_kernel_context_menu` takes a **dedicated branch at the top** (before the generic action build, D2/C5 pattern): a one-action menu **"Install from directory…"** → `QFileDialog::getExistingDirectory` → the C2 `install_from_directory()` → success ⇒ boot-instructions dialog (reusing `boot_instructions_for`, K8 pattern) + `init_kernels()` refresh (the C5 same-thread slot) so the installed kernel's row appears immediately. `on_configure` gains a one-line no-op guard when the current row is the pseudo row (else `apply_source_for_kernel` would prefill a nonsense source; :520-522).
- **Rejected:** (a) checkbox + Execute — the worker thread (`km-window.cpp:271-331`) cannot open a `QFileDialog` (cross-thread GUI = UB) and only sees `m_kernels` + change-list strings, so a widget-only row would need worker special cases; the info-row precedent already establishes non-checkbox interactivity; (b) a dedicated bottom-bar button — the user asked for "a new entry in the kernel list"; the row reuses the existing tree + context-menu machinery and needs **zero `.ui` changes** (the button would have needed one); (c) double-click trigger — the shared `itemDoubleClicked` → `check_uncheck_item` path (:421, :457-465) would set a phantom Checked state on the non-checkable row and append a phantom entry to `m_change_list`; right-click only (the established remediation pattern, D2). Row identity = the PkgName text compared against `tr("Install from directory…")` (both sides tr() ⇒ locale-consistent); a file-local `kDirectoryRowRaw` constant holds it.

### D2 (Feature A) — the install path = a pure planner in `install_kernel`, `pacman -U` of explicit quoted absolute paths (no shell glob) + the standard post-install tail
- **Chosen:** three new Qt-free additions in `src/install_kernel.{hpp,cpp}` (the module's existing style; `CommandRunner` contract reused):
  1. `[[nodiscard]] std::vector<std::filesystem::path> list_local_packages(std::string_view dir)` — `directory_iterator` over `dir` (non-recursive; a build dir holds the packages at its root, the post-build flow's layout), suffix `.pkg.tar.zst` (per the user request; the `get_pkgext_value_from_makepkgconf` PKGEXT generalization is documented as future work, not this cycle), sorted by filename for deterministic command strings.
  2. `[[nodiscard]] bool read_pkginfo(const std::filesystem::path& pkg, std::string& name_out, std::string& version_out)` — `utils::exec("tar --zstd -xOf '<pkg>' .PKGINFO 2>/dev/null")` (path single-quoted; space-safe; tar+zstd verified present), parse the `pkgname = ` / `pkgver = ` / `pkgrel = ` lines, `version = "<pkgver>-<pkgrel>"`; any failure ⇒ `false` (caller falls back to the filename stem — the install itself never depends on the parse).
  3. `struct DirInstallResult { bool ok; std::string error; std::string name; std::string version; std::vector<std::string> boot_instructions; };` + `[[nodiscard]] DirInstallResult install_from_directory(std::string_view dir, CommandRunner runner = CommandRunner{}, Bootloader bl = detect_bootloader())` — empty list ⇒ `ok=false`, error "no *.pkg.tar.zst packages found in '<dir>'", **zero runner calls**; else one escalated step `pacman -U '<abs1>' '<abs2>' …` (each absolute path single-quoted — **no shell glob**: the 0c918d4 absolute-path precedent plus a space-safe construction that also sidesteps the glob-expansion word-splitting pitfall) followed by `append_postinstall_tail(steps, bl)` **reused verbatim** (:50-55); `name`/`version` = the first package whose `.PKGINFO` parses to a non-`-headers` name (the kernel package), else filename stems; `boot_instructions = instructions_for(bl, name)` filled on every run (the `install_kernel` :96 pattern); execution loop identical to `install_kernel` :130-137 (first failing step ⇒ `ok=false`, error names the step + rc, remaining steps skipped; default runner = `run_real_command` :34-36).
- **Rejected:** (a) a shell glob `pacman -U <dir>/*.pkg.tar.zst` — works on normal names but word-splits on spaces after glob expansion and hides the actual file set from the planner (untestable without a shell); (b) reusing `Kernel::install()`/`commit_transaction()` — the row has no `Kernel` and the transaction model (global lists + one bulk `pacman -S`) doesn't fit a local-file install; (c) `--noconfirm` — the escalated terminal already shows pacman's own prompts (the whole install family uses bare `pacman -S/--needed`, D2-v1.23.0 parity); (d) skipping the post-install tail — a locally built kernel needs the initramfs refresh exactly like a repo one.
- **Uninstall:** no new code — the C1 local-DB row is a normal checked/immutable row; unchecking it flows through the existing `remove()` → `pacman -Rsn <name> <headers>` path (`kernel.cpp:222-254, 403-406`). Documented in the C1 spec, proven by the k11 relation in C4's audit.

### D3 (Feature A) — 4th `get_kernels` pass: locally installed kernels absent from every enabled repo appear as `local/<name>` rows
- **Chosen:** in `src/kernel.cpp`, after the curated info-rows pass (:386) and before `return kernels` (:388): `alpm_db_search` the **local** DB (`alpm_get_localdb(handle)`) with the same `linux[^ ]*-headers` needle (pass-1 pattern :287), skip `linux-api-headers`, derive the base, `alpm_db_get_pkg(local_db, base)` (null ⇒ skip — orphaned headers with no kernel installed), **dedup by `m_name` against all rows collected so far** (a repo/AUR row wins — the info-row dedup pattern :376-379), then `Kernel{handle, local_pkg, local_headers, "local", "local/<base>"}` (5-arg ctor; `m_headers` = the local headers package found by the needle). Result: the row has a real version (the `is_installed()` path of `version()` :142-156 compares local-vs-sync and both are the same local package ⇒ bare version), the right `category()`, Installed `✓`, and a Checked+Immutable checkbox (the tree block :225-232, `m_installed_db` empty on this libalpm) ⇒ **uninstall = uncheck + Execute** through the existing machinery. On this machine the pass is vacuous (every local kernel is in an enabled sync DB) — the harness asserts the relation, never the count.
- **Rejected:** (a) hardcoding a `m_installed_db`-based row — that API is absent in libalpm 16.0.1 (`HAVE_ALPM_INSTALLED_DB` off, k7 precedent); (b) adding the local row at widget level instead of data level — it must participate in `version()`/`remove()`/`is_installed()` (all `m_pkg`-based), and data level is what makes the "appears in the installed list" truth survive the worker's re-init (the worker's post-transaction rebuild :309-320 calls `get_kernels` — a widget-only row would reappear anyway via D1's `init_kernels_tree_widget` append, but the *installed kernel's* row would not exist at all without this pass); (c) a local DB pass that also re-lists kernels present in enabled repos — duplicates (hence the dedup).
- **K11 note:** k11 recomputes ground truth from `get_kernels` itself ⇒ self-consistent under the new pass (vacuous here); its count may drift with the environment — the pass gate is exit 0 + 0 FAIL, never an exact total (the v1.23.0 QA's k13 "62/62 vs actual 57" lesson, D6 note).

### D4 (Feature B) — `QSettings("ArchLinux", "KernelManager")` lazy accessors in `utils`; no `main.cpp` change; no cache
- **Chosen:** in `src/utils.{hpp,cpp}`: (1) `[[nodiscard]] std::filesystem::path build_repo_path() noexcept` — **ref→value** (the call sites are source-compatible, verified per site above): reads `QSettings` key `buildDir` on demand (a file-local `static QSettings settings{"ArchLinux", "KernelManager"};` — **explicit org/app** matching `main.cpp:126-129`, so the same file resolves in the app and in harnesses, and harnesses redirect it deterministically via `XDG_CONFIG_HOME`), falling back to `fix_path("~/.cache/kernel-manager/pkgbuilds")` (today's default, byte-identical behavior when unset). **No cache** — the accessor is called a handful of times per session (build flows), and on-demand reads make persistence trivially correct and testable. (2) `void set_build_dir(std::string dir) noexcept` — the `set_build_source_repo` pattern (:279-291): trim; empty ⇒ no-op (keep current); `~`-expanded via `fix_path`; written to the same `QSettings` key. (3) `[[nodiscard]] std::filesystem::path build_app_path() noexcept` — `build_repo_path().parent_path()` (the clone parent; default resolves to `~/.cache/kernel-manager` = today's `app_path` :294); `prepare_build_environment` (:293-296) switches to it (replacing the second hardcoded static).
- **Rejected:** (a) a `QSettings` init step in `main.cpp` (the brief's C7) — not needed: the explicit-arg instance is self-sufficient (no dependence on the app-singleton org/name), the identity values are the same constants, and a harness that never calls `main()` still resolves the right file; (b) the default singleton `QSettings()` — without a `QCoreApplication` its org/app would be empty in harnesses (a different, unresolvable file); (c) caching the path in a `static const` — a mid-session `set_build_dir` would not be visible (the whole point of the feature); (d) migrating an existing build tree on first pick of a new dir — the old dir is left as-is; `prepare_git_repo` re-clones on demand (the user's choice, not the app's business).
- **`<QSettings>` lands in `utils.cpp`** (Qt6Core is already a hard dependency of the module — `QProcess` :48 — and of every harness recipe that compiles it).

### D5 (Feature B) — the AUR build path derives from the same base: `<buildDir>/aur_pkgbuilds/<pkg>`
- **Chosen:** `src/aur_kernel.{hpp,cpp}` — the file-local `prepare_build_environment` (:32-36) stops hardcoding `~/.cache/kernel-manager/aur_pkgbuilds` and uses `utils::build_repo_path() / "aur_pkgbuilds"` (base) and `… / package_name` (per-pkg); the header's `detail` namespace gains `[[nodiscard]] std::filesystem::path aur_pkgbuilds_path(std::string_view package_name = {}) noexcept` (the base, or base/`<pkg>` — the exported seam that makes the derivation unit-testable in k15, mirroring `detail::install_aur_kernels` as the existing `detail` member).
- **Rejected:** (a) a second `QSettings` key for AUR — the brief says the AUR path derives from the same base; two keys would let them diverge; (b) keeping `fix_path` on the AUR sub-paths — the base is already expanded (fixing again is a no-op at best, wrong at worst if `buildDir` never contains `~`).
